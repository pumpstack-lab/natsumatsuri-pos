# こもれじ マルシェ対応（イベント切替＋カテゴリー階層）設計書

- 日付: 2026-09-25
- 発端: オーナー「今度マルシェがある。お祭り仕様からそっちに変更したい」「フード・ドリンクではなく物販になる。量が多いのでまずカテゴリーを選んで、その階層の中に個別の商品が出てくるようにしたい」
- 前提: レジ1台 / 商品20〜50品目 / カテゴリー3〜6つ / 商品リストはオーナーから受領しこちらで登録

---

## 1. 決定事項（オーナー確認済み）

| 項目 | 決定 |
|---|---|
| 端末台数 | 1台（レジ1つ） |
| 過去データ | **イベントごとに分けて残す**（祭りの売上も後から見返せる） |
| 実現方法 | 既存の `terminal`（窓口）をイベントとして使う＝**案A** |
| 画面構成 | 上にカテゴリータブ・下に商品 |
| 「すべて」タブ | **入れる**（先頭） |
| 会計後のカテゴリー | **先頭タブに戻る** |
| 金種 | 今のまま（¥50/¥100/¥500/¥1,000/¥5,000・商品券も残す） |
| 商品登録 | オーナーからリストを受領し初期データ化。当日の追加・変更は現場でも可 |

## 2. なぜ案A（terminalをイベントとして使う）か

`terminal` は既に「売上をグループに分け、選んだグループだけ表示する」仕組みとして完成しており、イベント分割と構造が同一。売上・商品・顧客番号の採番・Excel出力・合算履歴の全経路が既に対応済み。

- **祭りのデータを1行も触らない**（`terminal: 'food' / 'drink'` はそのまま残る）
- DBマイグレーション不要
- 実装は「値を1つ足す」＋「画面の言葉を変える」が中心

**却下した案**
- 案B（`event` を新フィールドで追加）: 売上・同期・Excelの全経路に新フィールドを通す必要があり、既存データの移行も要る。イベント×窓口の掛け合わせは今回1台運用なので不要
- 案C（マルシェ専用に作り替え）: 「イベントごとに残す」を満たせない

**案Aのトレードオフ（オーナー承諾済み）**
将来マルシェを2台運用にする場合、イベントと窓口を掛け合わせられない。`marche_reji1` のような命名で回避は可能だが整理されない。今回は1台なので割り切る。

## 3. データ設計

### 3.1 イベント（terminal）

```js
// src/core/events.js（新規）
export const EVENTS = [
  { id: 'marche', name: 'マルシェ',        icon: '🛍', hasCategories: true },
  { id: 'food',   name: 'フード（夏祭り）',  icon: '🍔', hasCategories: false },
  { id: 'drink',  name: 'ドリンク（夏祭り）', icon: '🥤', hasCategories: false },
];
```

- 既存の `food` / `drink` はラベルを「（夏祭り）」付きに変えるだけ。**保存済みの売上の `terminal` 値は変更しない**
- 金種テーブル `CASH_UNITS_BY_TERMINAL` に `marche` を追加（food と同じ5種）

### 3.2 カテゴリー

商品に `category`（文字列）を1つ持たせる。

```js
{ id: 'm1', terminal: 'marche', name: 'クッキー', price: 300,
  category: '焼き菓子', sort_order: 0, is_available: true }
```

- **既存の祭り商品は `category` を持たない**（undefined）。カテゴリーが1つも無いイベントではタブを描画しないので、祭りの画面は現状のまま
- カテゴリーの表示順は、**そのカテゴリーに属する商品の `sort_order` の最小値**の順。
  初期データを「カテゴリーごとにまとめた順」で並べておけば、意図した順にタブが出る。
  商品を並び替えればタブ順も追随する（カテゴリー順という別概念を作らない）

## 4. 画面

### 4.1 トップ

「どちらの窓口ですか？」→ **「どのイベントですか？」**。`EVENTS` を縦に並べ、各カードに組数と売上を出す（既存の `terminalStats` をそのまま使う）。

### 4.2 レジ画面

商品グリッドの上にカテゴリータブを追加。

- 先頭が「すべて」、以降は商品から導出したカテゴリー
- カテゴリーが0個のイベント（祭り）ではタブ自体を描画しない
- 選択中のカテゴリーは `state.category`（メモリのみ・端末に保存しない）。
  アプリを開き直すと先頭（すべて）から始まる
- 会計完了（`resetCart`）で先頭タブに戻す
- 商品が7品以上なら既存の `--dense`（4列）を継続適用。**判定対象はタブで絞った後の商品数**

### 4.3 商品の設定画面

商品の追加・編集時にカテゴリーを入力できるようにする（現状は商品名・価格の2つのprompt→カテゴリーを追加して3つ）。

## 5. Excel出力

- 出力単位は現状どおり「今選んでいるイベント」
- **商品別シートに「カテゴリー」列を追加**（商品名の左）。カテゴリーが無い商品は空欄
- 明細・サマリーシートは変更しない（既存の合算テンプレートを壊さない）

## 6. 影響範囲と非変更点

**変更するファイル**
- `src/core/events.js`（新規）
- `src/core/products.js`（マルシェ商品の初期データ・カテゴリー導出関数）
- `src/core/cash.js`（marche の金種）
- `src/core/exportsheets.js`（商品別シートにカテゴリー列）
- `src/ui/screen-top.js`（イベント選択）
- `src/ui/screen-register.js`（カテゴリータブ）
- `src/ui/screen-products.js`（カテゴリー入力）
- `src/ui/state.js`（`state.category`）
- `styles.css`（タブのスタイル）

**触らないもの（重要）**
- 保存済みの売上データ（`sales` ストア）— 祭りの記録はそのまま
- `src/core/sale.js` / `syncrow.js` / `db.js` — 保存形式・同期形式は不変
- 明細・サマリーシートの列構成 — 既存の合算テンプレートが動き続ける
- 預かり金・お釣り・商品券・職員販売・取消のロジック

## 7. テスト方針

- `events.js` / カテゴリー導出 / カテゴリー付き商品別シート: 単体テスト
- **祭りの既存商品（category なし）でタブが出ないこと**を単体で守る（退行防止）
- 実ブラウザ検証 `scripts/verify_marche.py`（新規）:
  1. イベント選択 → マルシェに入る
  2. カテゴリータブが並ぶ・タップで商品が入れ替わる
  3. 「すべて」で全商品が出る
  4. 会計を通す → 先頭タブに戻る
  5. **イベントを祭りに切り替えて、祭りの売上と商品が無傷で出る**
  6. Excel書き出し → 実ファイルを開いてカテゴリー列を確認
- 既存の `verify_cash500.py` / `verify_prices_cash50.py` / `verify_product_sheet.py` を回帰として全通し
